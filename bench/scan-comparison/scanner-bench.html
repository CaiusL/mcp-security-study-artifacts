MCP Scanner Bench

Seven scanners, including our own zgScanner, ran against five hosted MCP servers picked at random. I then reviewed every definition by hand as a control. None of the five shows malicious content. The control rates Veterical High: a skill it serves breaks its own read-only promise and pre-approves an unpinned npx command. No scanner explained that. Cisco's scanner came closest overall. zgScanner caught one of the four main issues, with the right reason.

Control review

Claude's own read of the five servers

Same rule as the scanners: initialize, the list calls and resource reads, and no tool calls. I fetched everything fresh. I read all 51 tool definitions in full, with the instructions, annotations, schemas, _meta and both skill files. Evidence: control/CONTROL-REVIEW.md.

HIGH

Veterical

11 tools · 6 resources
  • The connector's instructions promise an administrative, read-only boundary: no owner or animal records, and no tools that create, update or delete anything.
  • The same server serves skill://veterical/veterical/SKILL.md and declares the MCP skills extension. That skill drives the veterical CLI with full create, update and permanent delete of clients, patients, appointments, invoices, payments and vaccination records. missed by all scanners
  • Its header sets allowed-tools: Bash(npx veterical:*). In clients that honor that field, this pre-approves running an unpinned npm package on the user's machine. It also covers account signup and a device-code login.
  • In mitigation, it is the vendor's own CLI, and the skill says to confirm deletes and keep keys out of transcripts. The tools themselves are careful, and the HTML widgets ship a strict CSP that blocks forms and network calls.
MEDIUM

Hallux

4 tools · 2 resources
  • It receives every install command and full dependency file. These can carry private package names and index URLs with embedded tokens.
  • For a deprecated or blocked name, the agent is told to use the server's successor. So the server can choose which package gets installed instead. missed by all scanners
  • It inserts itself before every install ("Call this BEFORE..."). That fits its purpose, but it is still steering.
  • It fails closed (unknown is never permission), and the annotations are honest about hallux_watch writing.
MEDIUM

WealthMCP

8 tools
  • get_skill returns runtime workflows that the agent is told to follow exactly. That content is not in the metadata.
  • The instructions say to relay install commands and config snippets from listings verbatim, and some listings are "Community". A bad listing would reach the user as a ready-to-run install line. missed by all scanners
  • When tools differ from server_info, the agent is scripted to blame a stale client cache. With listChanged: true, this normalizes the change a rug-pull check looks for.
LOW

AIK Stock Data

12 tools
  • The instructions and get_data_urls push the agent to call that tool "before concluding something is unavailable", then to fetch dataset URLs with its own fetch tool, outside MCP.
  • A read-only data server with a clear not-investment-advice notice. The scanners' "prompt injection, High" overstates it.
CLEAN

Vuntum

16 tools
  • Sixteen read-only lookups. The instructions tell the agent not to follow quoted source text.
  • Tool output includes third-party quotes and repository text, so some injection risk exists at runtime, and the server says so. openWorldHint: false is arguably inaccurate for that content.

Checks run on all five

  • noneTool changes since this morning's fetch
  • noneDifferent tools when the client says it is claude-ai
  • noneTools hidden past a pagination cursor
  • noneZero-width, bidi or tag characters, ANSI codes, encoded payloads
  • cleanVeterical's base64 SVG icon: no script, handlers or links
  • strict CSPVeterical's four HTML widgets, pattern-scanned and spot-read

Limits: this control is not blind, because I had already seen the scanner output and part of the metadata. Without tool calls, runtime output stays unseen: WealthMCP's skills, AIK's URL catalog and Hallux's successor values. These are judgments from metadata, not a code audit. An LLM reviewer can also be steered by the text it reads. Nothing here was addressed to me, and I treated all of it as data.

Our scanner

zgScanner in detail

Run once per server: python -m wiggle.zgscanner scan <url> --no-discover --no-skills. Pasted URLs turn off config and skill discovery, and only the pasted server is contacted. The LLM judge did not run, because the anthropic package and a key are not installed.

What it got right

  • Its toxic-flow check (TF007) described Hallux's real risk most accurately of the seven: one server both reads private data (dependency files) and has an outbound sink (the webhook).
  • It did not flag the word "auth" or $schema links, the two patterns behind most of fr2endly's noise.
  • It noted that WealthMCP and Vuntum can change their tool list at runtime (RP004). That is the precondition for a rug pull.
  • Each finding names its check ID, its OWASP MCP tag and the scanners whose feature it reproduces, which made triage fast.

What it missed or got wrong

  • Resources are listed but never read. Live introspection stops at resources/list, so the Veterical SKILL.md was never seen. A resources/read for text types would have caught signal 1.
  • No rule for steering language. Phrases like "follow the skill exactly" or "call this before concluding" pass the static rules. That missed signals 2 and 4. The LLM judge might cover them, but it was not tested here.
  • SC002 false positives. A free-string argument whose description says "URL identifier" counts as a URL. That made the 6 Medium findings on Vuntum's slug arguments.
  • TP016 false positives. It matched "publish" and even "do not run the command" against readOnlyHint. That caused the Medium findings on AIK and Hallux.
  • No check on skills served over MCP. Veterical's skill pre-approves npx commands and contradicts the connector's own boundary. That is a Declared-versus-Reachable gap of exactly the kind the wiggle study measures. With --no-skills and no resource reads, zgScanner could not see it.
  • 23 of its 67 checks were skipped. They need source code, skills, pins, OSV, VirusTotal, an allowlist or the LLM.
Method

How this was run

Picking the servers

I took random listing pages (40, 84, 107, 113) on mcpservers.org and kept third-party entries: no "official" or "sponsor" badge, a hosted URL, and a tool list that loads without a key. Of 34 candidates probed, 17 answered; 5 were drawn at random from those. Listings older than about page 130 are almost all local packages, so testing them would mean running unknown code on this PC. They were left out.

What was sent to the servers

Only initialize, the tools, prompts and resources list calls, and resource reads. No tool was called. The site rate-limited the listing crawl after about 60 page loads, so later pages could not be sampled.

Scanner setup

  • Cisco: main @10032f9 with local fixes; LLM is DeepSeek deepseek-flash.
  • Ramparts 0.8.10: Linux build through WSL with YARA rules, no LLM.
  • MCP-Shield 1.0.4: patched for Streamable HTTP, no Claude key.
  • Nova-Proximity @d752174: keyless, so only the DetectJailbreaking keyword rule ran.
  • mcp-fence 0.1.2: static config scan only; it reports "Live inspection unavailable".
  • fr2endly mcp-scan @12fe4a1, drift snapshots off.
  • zgScanner 0.1.0 (wiggle), static rules plus live list calls.

Control review

After the scans, I fetched the servers fresh, then again under the client name claude-ai. I followed every list's pagination and read every resource. Then I read every definition. Scripts ran the hidden-character and encoded-payload checks; the judgments are mine.

Files

Everything is in C:\Test\scan-comparison. raw/ holds each server's metadata, and there is one folder per scanner. zgscanner/<host>/report.json holds zgScanner's full results. cisco/rerun-4000tokens.txt and cisco/resources-markdown-json.txt are the two follow-up Cisco runs. control/ holds the control fetch and review.
