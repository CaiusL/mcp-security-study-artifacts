# Static and metadata-based MCP security scanners: catalog, evaluations, and coverage limits

Research date: 2026-10-24. GitHub stars, last-push dates, and release tags were read from the GitHub REST API on 2026-10-24 (calls to `api.github.com/repos/<owner>/<repo>` and `/releases`). Vendor statements are marked "vendor claim". Self-reported results from a tool's own authors are marked "self-reported".

## Q1. Scanner catalog: checks, static vs runtime, LLM use, data sent off-machine, license, repo, activity

### Takeaway
Most public MCP scanners are pre-deployment tools. They read configs, tool/prompt/resource metadata, and sometimes source code, using YARA/regex rules, sometimes with an optional LLM judge. Only a few run in the request path: Trail of Bits mcp-context-protector, the Lasso gateway, and the historical `mcp-scan proxy`. The best-known scanner, Snyk Agent Scan (formerly Invariant mcp-scan), sends tool descriptions to a Snyk cloud API. Its current CLI no longer has the `proxy` subcommand. Three of zgScanner's source URLs now redirect. The AgentAvow repo is archived.

### Inferences
- On 2026-10-25 the catalog URLs for Ramparts, Proximity, and AgentAvow were resolved through the GitHub API. `getjavelin/ramparts` redirects to `highflame-ai/ramparts` (tag v0.8.10, commit `70457dbf`). `fr0gger/proximity` redirects to `Nova-Hunting/nova-proximity` (no tags; main `d7521742`, 2026-03-26). `AgentAvow/mcp-security-scan` is archived (tag v1.1.0, commit `5fe94a4d`). Snyk already pointed at `snyk/agent-scan`. The feature rows were read from READMEs on 2026-10-20 without a commit, so those SHAs identify the repositories and do not pin each check to a line. Several sources look dormant: MCP-Shield (last push 2025-04), MCPSafetyScanner (2025-04), and Agentic Radar (2025-11).
- zgScanner is stdlib-only and makes no network calls. It therefore cannot reproduce checks that depend on a cloud API or an LLM: Snyk's server-side classifiers, Cisco's LLM and behavioral analyzers, the LLM conditions in Proximity/NOVA, and MCPSafetyScanner's agents. Its merged checks are best described as the rule-based subset of these scanners.
- "Static vs runtime" is a spectrum. Many "static" scanners still start or connect to the server to read `tools/list`, which means they run untrusted code. Snyk stopped launching stdio servers by default in v0.5.9 for this reason.

### Gaps
- The CHANGELOG has no entry for when `mcp-scan proxy` was removed, and none for whether the local tool-hash pinning store still exists in v0.6.x. The v0.5.x/v0.6 docs list no "tool changed" code.
- Snyk/Invariant have never published whether the analysis API uses an LLM, a fine-tuned classifier, or rules.
- I found no technical page for Pillar Security MCP scanning. The search returned only generic vendor roundups.
- I found no GitHub-specific (github.com/mcp) registry security checks. Only the official MCP Registry's namespace checks were documented.
- Smithery: the only scanning evidence is the April 2025 Invariant partnership. The current status is unknown, and `smithery-ai/cli` now redirects to `arcadeai-labs/smithery-cli`.

## Q2. Published evaluations of scanner effectiveness (precision/recall, false positives, misses)

### Takeaway
Every independent evaluation found low recall, high false-positive rates, or both. On 37,288 real servers, the eight scanners averaged 45.53% precision and 24.17% recall on a CVE ground truth, with only 15.66% average pairwise agreement (MCPZoo, 2026-07-13). Several studies show directly that manifest/metadata scanners miss malice that lives in code, appears only at runtime, or arrives through channels other than tool metadata. In the ACE corpus, 52 of 82 malicious tampered-MCP fixtures did not change `tools/list`, and 51% of the corpus had no MCP server to scan. No study yet tests the exact hypothesis (an allowed tool on an allowed resource used for the attacker's goal), but the closest evidence supports it.

### Cited Findings

**Academic evaluations (independent of the scanner vendors)**
- **MCPZoo / "Rethinking MCP Security"** (Chen et al., Fudan, arXiv 2607.11086, 2026-07-13): 8 scanners on 37,288 dynamically runnable servers. 96.89% of servers were flagged by at least one scanner. Precision came from 100 sampled risky servers with two reviewers (κ = 0.87). Recall came from 10 CVEs affecting 38 servers. Results: Agent-Scan (Snyk) P 28.21% / R 50.00%; A.I.G static 56.98% / 47.06%; A.I.G dynamic 10.40% / 5.88%; Cisco MCP-Scanner 24.64% / 21.21%; Ant MCPScan 45.53% / 74.29%; MCPSafetyScanner 74.03% / 0.00%; Lasso mcp-gateway 96.88% / 0.00%; nova-proximity 52.78% / 0.00%; mcp-armor 20.34% / 19.05%. Averages: precision 45.53%, recall 24.17%, pairwise Jaccard 15.66%. Metadata-based scanners rely on descriptions/schemas, "lacking visibility into implementation and execution paths"; in one example, a metadata scanner missed ecommerce-store-mcp because its description looked benign. LLM backend: Qwen3-235B-A22B-Instruct — [arXiv:2607.11086](https://arxiv.org/html/2607.11086v1)
- **MalTool** (Hu, Jia, Li, Song, Gong; arXiv 2602.12194, v1 2026-02-12, v3 2026-05-09): Dataset I has 1,300 standalone malicious tools (13 behaviors × 100). Dataset II has 5,727 trojaned real tools. Dataset III has 4,846 benign tools from 1,147 repos. Dataset I false-negative rates: Cisco MCP Scanner 0.010–1.000, Ant MCPScan 0.130–1.000, Tencent A.I.G 0.240–0.960, VirusTotal 1.000 on all behaviors. Benign false-positive rates: Cisco 0.000–0.019, A.I.G 0.222–0.471, MCPScan 0.257–0.588, VirusTotal 0.000. Accuracy across all three datasets: Cisco 0.447, A.I.G 0.411, MCPScan 0.375, VirusTotal 0.307, combined 0.814. Resource hijacking and DoS behaviors were "almost universally missed". The authors call for defenses that check whether code is consistent with the description — [arXiv:2602.12194](https://arxiv.org/html/2602.12194v3)
- **ACE / "On the Effectiveness of Kernel-Level Evidence for Agent Security"** (King et al., arXiv 2609.28915, 2026-09-24), Appendix L.1: Cisco mcp-scanner v4.8.1 in offline mode (all 10 YARA rule sets, no LLM) on 1,871 tampered-MCP sessions (731 positives). Recall 0.159 at 16.3% FPR. Trained cross-layer detectors scored 0.917–0.981 recall at 2.6–4.0% FPR. Reasons given: (1) YARA anchors on verbatim phrases and misses paraphrased coercive injection, so it "does not detect the attack *class*"; (2) 52 of 82 malicious fixtures change server behavior without changing `tools/list`; (3) 5 of 6 delivery-vector families (51% of ACE) deliver payloads through files, web responses, user prompts, memory, or retrieved documents, with no MCP server to scan. The authors call this "a structural blind spot of the scanner class" — [arXiv:2609.28915](https://arxiv.org/html/2609.28915v1)
- **MalSkillBench** (Guo et al., arXiv 2606.07131, 2026-06-05; skills, not MCP servers): 3,944 malicious skills (runtime-verified) and 4,000 benign. Snyk Agent Scan: precision 93.2%, recall 28.7%, 82 FP. Cisco Skill Scanner: static recall 35.6%; LLM mode recall 92.7% with 1,465 FP. AI-Infra-Guard F1 85.6%. VirusTotal recall 21.6%, 4 FP. Signature/static scanners need "compact, explicit indicators". Cisco static recall on prompt-injection skills was only 18.7%. Wild-only evaluation inflates scores: VirusTotal recall rises to 87.9% on the wild subset — [arXiv:2606.07131](https://arxiv.org/html/2606.07131v1)
- **MCP-DPT** (Rostamzadeh et al., ODU, arXiv 2604.07551, 2026-04-08): classifies MCP-Scan, MCPScan.ai, Cisco MCP Scanner, and MCP-Shield as "static/pre-execution only". Such tools "do not monitor live agent behavior and therefore do not provide runtime enforcement". Coverage is architectural applicability, not measured accuracy. MCP-Scan covers 83% of registry/supply-chain capabilities; transport/network is almost entirely uncovered — [arXiv:2604.07551](https://arxiv.org/html/2604.07551)

**Practitioner / vendor-adjacent evaluations**
- **Pluto Security**, "Malicious Servers, Clean Scans" (Perkal and Chassid, 2026-09-15): tested a hidden credential thief and a hidden RCE server. Both had benign weather metadata, with the malice in handler code; the RCE command was fetched at call time. Cisco (YARA, metadata LLM, behavioral), Snyk cloud scan, Ventrova sentinel, and MCP-Shield all missed both. All caught the "confessing" positive control. Only NVIDIA SkillSpector's default LLM review caught both, and only at normal file size; padding the file past its size limit evaded it. Evasions shown: runtime-assembled strings, XOR/hex payloads, client-name switching (benign description returned to scanner clients), and tool-result injection. Cisco's behavioral prompt (72,798 chars) exceeded its 68,000-char limit, so incomplete analysis "looks clean" — [Pluto Security](https://pluto.security/blog/malicious-mcp-servers-clean-scans/)
- **AppSec Santa audit** (Cankurt, updated 2026-07-02): 33 local servers, 433 tools. Cisco mcp-scanner v4.3.0 made 27 detections; the author judged about 78% false positive (8 were standard "call this first" instructions, 10 were designed functionality, 3 clear FPs; 6 genuine). MCP-Scan v0.4.3 made 37 findings, including 33 "server mutations" the author judged mostly benign. mcp-audit v0.14.1 found 4 confirmed open endpoints and one typosquat FP — [AppSec Santa](https://appsecsanta.com/research/mcp-server-security-audit-2026)
- **WARDEN comparison** (author of a competing scanner, "We are not neutral"; 2026-10-09): held-out MCPTox set of 218 poisoned tools. mcp-shield 1.0.4 caught 41 (19%), mcp-audit 0.18.2 caught 25 (11%), WARDEN v10 caught 171 (78%; rules written knowing the templates). On 986 remote registry servers, mcp-shield blocked 343 (about 35%) and 0 of 20 sampled blocks held up. mcp-audit blocked 33, none valid. With the benchmark's injection prefix added, detection was near 100%, which shows rule scanners key on surface markers — [dev.to](https://dev.to/alexar76/we-ran-three-mcp-security-scanners-on-a-tool-poisoning-benchmark-and-986-real-servers-1klb)
- **mcp-sec-bench scoreboard** (2026-09-17, synthetic corpus, 10 attack classes A1–A10 split into metadata, live behavior, and source code): Cisco mcp-scanner and Ramparts both had recall 0.00; mcp-guard (SaravanaGuhan) 0.50 recall / 0.67 precision; sentinel-scan-cli 0.17 recall. Snyk agent-scan 0.6.3 was not measured (token required). The page says "A high score here is not a safety certification." — [mcp-sec-bench](https://falc0n007.github.io/mcp-sec-bench/)
- **Docker agentic audit** (vendor, 2025-12-03): LLM agents review code diffs. No accuracy figures; "haven't run across anything malicious so far" — [Docker](https://www.docker.com/?p=83505)

**Self-reported detector results (authors' own method and data)**
- FlowGuard (Fudan, arXiv 2607.14754, 2026-07-16): uses runtime evidence. F1 0.879 on command injection and 0.942 on file-system access, on a 1,880-case executable benchmark. Motivation: existing scanners "primarily reason about suspicious semantic signals rather than real execution behaviors" — [arXiv:2607.14754](https://arxiv.org/abs/2607.14754)
- Enkrypt (vendor claim): "0 false positives in critical findings", "98% accuracy"; no method published — [Enkrypt blog](https://enkryptai.com/blog/we-scanned-1-000-mcp-servers-33-had-critical-vulnerabilities)

### Inferences
- The evidence supports the hypothesis in its weaker form: static/metadata scanners catch explicit metadata poisoning and config smells, and miss (a) code-level malice, (b) behavior that appears only at call time, (c) payloads in tool outputs or other runtime content, and (d) paraphrased injections. ACE's "51% has no MCP server" result and Pluto's tool-result-injection result are the closest analogues to "in-scope misuse": there is nothing malicious in the artifact the scanner reads.
- Scanner outputs barely overlap (Jaccard 15.66%). Merging checks from many scanners, as zgScanner does, will raise recall on metadata-visible issues. It will also add each scanner's false positives, and MCP-Shield and Cisco YARA have FP rates of about 35% and about 78% in the practitioner studies above. The study should report zgScanner's FP rate on a benign server set, not only its hits.
- Results depend heavily on the benchmark. Synthetic markers inflate recall (the injection-prefix result), wild-only sets inflate recall (MalSkillBench), and LLM modes trade precision for recall.

### Gaps
- No published study evaluates a scanner against attacks with **no malicious artifact at all** (benign server, benign metadata, injected goal through data, allowed tool misused). This is the study's niche.
- No independent evaluation of Ramparts, MCP Watch, mcpguard, AgentAvow, or mcp-context-protector beyond the synthetic mcp-sec-bench row for Ramparts.
- MCPZoo gives no per-category miss breakdown and no version numbers.

## Q3. OWASP MCP Top 10, OWASP LLM/Agentic Top 10s, CoSAI, MITRE ATLAS: versions, dates, categories, static-scan coverage

### Takeaway
The OWASP MCP Top 10 is still a "beta" list with 2025-suffixed IDs (MCP01–MCP10). The OWASP Agentic Top 10 for 2026 was published 2025-12-09. The OWASP LLM Top 10 v2025 was published 2024-11-18. CoSAI's MCP Security paper (Draft) was approved on 2026-01-08 and defines MCP-T1–T12. MITRE ATLAS added MCP-relevant techniques from late 2025: AML.T0104 Publish Poisoned AI Agent Tool, AML.T0109 AI Supply Chain Rug Pull, and AML.T0110 AI Agent Tool Poisoning, plus postmark case study AML.CS0053. Static scanning maps well to MCP01, MCP03, and MCP04 (partial), and poorly to MCP06, MCP10, and the agentic runtime categories (ASI01 goal hijack, ASI02 tool misuse).

### Inferences
Coverage of each OWASP MCP category by static/metadata scanning. This is my mapping, based on the scanner check lists in Q1 and the misses in Q2:
- **Good coverage**: MCP01 secrets (regex/entropy in configs and code); MCP03 tool poisoning, but only explicit, at-scan-time, non-paraphrased poisoning (see Q2 and Q4).
- **Partial coverage**: MCP02 (can flag wildcard `alwaysAllow` or broad scopes, cannot see privilege actually used); MCP04 (unpinned `@latest`, OSV CVEs, typosquats; misses backdoors in code unless code analysis is in scope, as with postmark-mcp); MCP05 (needs source-code SAST, which metadata-only scanners cannot do); MCP07 (can flag HTTP without auth or probe open endpoints); MCP09 (config discovery finds servers on the scanned machine only).
- **Little or no coverage**: MCP06 prompt injection via contextual payloads (arrives at runtime in tool outputs/resources; see ACE and Pluto); MCP08 audit/telemetry (a config can show logging exists, not that it is effective); MCP10 context over-sharing (only a capability proxy, such as Snyk's W017/W018 data-exposure flags).
- For the Agentic Top 10, ASI02 Tool Misuse and ASI01 Goal Hijack are the study's "in-scope misuse" categories. A static scanner can at most flag risky capability combinations (Snyk's "toxic flow" components W015–W020). It cannot tell whether a given call serves the user or the attacker. ATLAS AML.T0086 says the same for exfiltration: the tool itself may be legitimate.

### Gaps
- No exact version number or release date for the OWASP MCP Top 10. I did not read the per-category pages for detection guidance.
- The Agentic Top 10 category names come from secondary sources. The OWASP PDF was not opened.
- ATLAS: newer technique IDs may exist in the v2026.09 release, which uses a non-deprecated data layout I did not parse.

## Q4. Tool-description poisoning detectors: reported accuracy and known bypasses

### Takeaway
Learned detectors report high accuracy on their own benchmarks: MCP-Guard's E5 stage 96.01% accuracy, MindGuard 94–99% average precision, supervised ML up to 100% binary F1. These are all self-reported on synthetic or self-built data. Adaptive attacks break LLM-based detection: MCP-ITP pushed the detection rate down to 0.3% while reaching up to 84.2% ASR. Practitioner tests show rule detectors miss paraphrase, client-specific metadata, and runtime-delivered payloads.

### Cited Findings
- **MCP-Guard** (Xing et al., arXiv 2508.10991; v1 2025-08-14, v4 2026-01-08): three stages. (1) Static pattern scan: 74.55% accuracy, 97.67% precision, 38.89% recall. (2) Fine-tuned E5 detector: 96.01% accuracy, 95.06% F1, up from 65.37% before fine-tuning. (3) LLM arbitrator. The full pipeline reported 89.63% accuracy / 89.07% F1 in v1. Benchmark MCP-AttackBench has 70,448 GPT-4-augmented samples. All results are self-reported on the authors' own benchmark — [arXiv:2508.10991](https://arxiv.org/abs/2508.10991), [PDF](https://arxiv.org/pdf/2508.10991)
- **MindGuard** (Wang et al., arXiv 2508.20412; 2025-08-28, v3 2026-01-15): a decision-level guardrail that uses attention-based Decision Dependence Graphs. Self-reported 94–99% average precision and 95–100% attribution accuracy, under 1 s, no extra tokens. It argues behavior-level defenses fail against tool poisoning because "poisoned tools need not be executed, leaving no behavioral trace". It needs white-box model access (attention) — [arXiv:2508.20412](https://arxiv.org/abs/2508.20412)
- **ML-Based Detection of MCP Attacks** (Mattsson et al., arXiv 2604.10534, 2026-04-12): supervised models on malicious tool descriptions. "Several" models reached 100% F1 in binary classification; in multiclass, SVC scored 90.56% F1 and BERT 88.33%, compared with a rule baseline — [arXiv:2604.10534](https://arxiv.org/abs/2604.10534)
- **MCPTox** (Wang et al., arXiv 2508.14925; 2025-08-19, v2 2026-09-29; AAAI 2026 per the WARDEN post): 45 live servers, 353 tools, 1,348 poisoned cases, 3 templates. o1-mini ASR 72.8%; "more capable models are often more susceptible" — [arXiv:2508.14925](https://arxiv.org/abs/2508.14925)
- **Bypass – MCP-ITP** (Li et al., arXiv 2601.07395, 2026-01-12): implicit tool poisoning. The poisoned tool is never invoked; its metadata steers the agent to call a legitimate high-privilege tool. Black-box optimization with feedback from an evaluator LLM and a detector LLM reached up to 84.2% ASR, with Malicious Tool Detection Rate as low as 0.3%, across 12 agents on MCPTox. The detector in the loop is a simulated LLM detector, not a named commercial scanner — [arXiv:2601.07395](https://arxiv.org/abs/2601.07395)
- **Bypass – paraphrase**: Cisco's YARA `coercive_injection` rule matches verbatim phrases, so paraphrases of the same intent evade it (recall 0.159) — [arXiv:2609.28915 App. L.1](https://arxiv.org/html/2609.28915v1). With an explicit injection prefix, rule scanners caught 222–225 of 225 tools; without it, they caught 11–19% — [WARDEN post](https://dev.to/alexar76/we-ran-three-mcp-security-scanners-on-a-tool-poisoning-benchmark-and-986-real-servers-1klb)
- **Bypass – client switching, size limits, truncation**: a server returned benign metadata to known scanner client names; padding a file past SkillSpector's size limit skipped its LLM review; Cisco's behavioral prompt was over its limit — [Pluto Security](https://pluto.security/blog/malicious-mcp-servers-clean-scans/). MCP-Shield's `--identify-as` option exists to probe for this client-dependent behavior — [MCP-Shield](https://github.com/riseandignite/mcp-shield)
- **Normalization defenses**: Ramparts runs its YARA rules on text with zero-width characters removed and homoglyphs folded, and on base64/hex-decoded content — [Ramparts](https://github.com/highflame-ai/ramparts). Snyk flags hidden Unicode (W021) — [issue-codes.md](https://github.com/snyk/agent-scan/blob/main/docs/issue-codes.md)

### Inferences
- High in-distribution accuracy (MCP-Guard, 100% binary F1) probably reflects synthetic template data. MCP-ITP and the paraphrase results suggest these numbers will not hold under adaptive attackers. No study re-tests MCP-Guard's E5 detector against MCP-ITP-style descriptions.
- Implicit tool poisoning sits between the two categories in the study's hypothesis. The poison is in metadata, so a static scan can see it in principle. The harmful action, however, is an allowed tool used in scope, which is what runtime layers must stop if the scan misses the metadata.

### Gaps
- I found no published bypass that targets MCP-Guard or MindGuard specifically.
- I found no independent replication of any learned tool-poisoning detector on a held-out real-world set.

## Q5. Rug-pull detection through pinning/hashing, and rug pulls in the wild

### Takeaway
Description pinning is implemented by Trail of Bits mcp-context-protector (runtime TOFU, blocks on change), historically by Invariant mcp-scan (tool hashing), by Ramparts (content fingerprinting), by AgentAvow's hosted service, and statically by MCP Watch (a "tool mutation" check). Docker pins code at the commit level. The documented in-the-wild case, postmark-mcp (malicious v1.0.16 on 2025-09-17 after 15 clean versions), was a code-level change. Tool-description pinning would probably not have detected it. Pinning also produces benign drift alerts.

### Cited Findings
- **mcp-context-protector**: compares server instructions, tool descriptions, and input schemas against approved configs stored in `~/.mcp-context-protector/servers.json`. The comparison is semantic and order-insensitive. Any deviation blocks tool calls until a user approves. It rechecks on `tools/list_changed` — [Trail of Bits](https://github.com/trailofbits/mcp-context-protector)
- **Invariant mcp-scan**: "tracking changes through tool hashing" to detect rug pulls (2025-04-11) — [Invariant blog](https://invariantlabs.ai/blog/introducing-mcp-scan). In practice, MCP-Scan v0.4.3 reported 33 "server mutations" on 33 servers, which the auditor judged "mostly benign" — [AppSec Santa](https://appsecsanta.com/research/mcp-server-security-audit-2026). The current Snyk docs (v0.5.x issue codes, v0.6 risks) list no description-change finding — [issue-codes.md](https://github.com/snyk/agent-scan/blob/main/docs/issue-codes.md), [risks.md](https://github.com/snyk/agent-scan/blob/main/docs/risks.md)
- **Ramparts**: "rug-pull or drift detection through content fingerprinting" — [Ramparts](https://github.com/highflame-ai/ramparts)
- **AgentAvow**: the hosted scanner offers "tool-definition pinning, and drift detection across re-scans"; a local one-shot scan "structurally can't" — [AgentAvow](https://github.com/AgentAvow/mcp-security-scan)
- **MCP Watch**: static "tool mutation (dynamic changes, rug-pull risk)" check — [MCP Watch](https://github.com/kapilduraphe/mcp-watch). **mcpguard**: lists rug pulls under MCP03 patterns — [mcpguard](https://github.com/loplop-h/mcpguard)
- **Docker**: pins each server to a Git commit (`source.commit`, CI-enforced). Every pin bump gets an LLM-agent code review; critical findings block merging. The post does not mention tool-description monitoring — [Docker blog, 2025-12-03](https://www.docker.com/?p=83505)
- **MCP-DPT**: a registry can evaluate only static metadata at submission time, while rug-pull behavior may appear only at runtime in the host — [arXiv:2604.07551](https://arxiv.org/html/2604.07551)
- **postmark-mcp (in the wild)**: an npm impostor of Postmark's library. Koi Security reported 15 clean versions, then v1.0.16 (reported release 2025-09-17) added a one-line BCC of every email to an attacker address. 1,643 total downloads; Koi estimated about 300 organizations compromised (estimates vary, up to about 1,500 in other outlets). The publisher deleted the package — [The Hacker News](https://thehackernews.com/2025/09/first-malicious-mcp-server-found.html), [CSO Online](https://www.csoonline.com/article/4064009/trust-in-mcp-takes-first-in-the-wild-hit-via-squatted-postmark-connector.html). MITRE models it as case study AML.CS0053 and defines the general pattern as AML.T0109 AI Supply Chain Rug Pull ("publish legitimate AI components... then push an update with a malicious variant") — [ATLAS data](https://github.com/mitre-atlas/atlas-data)
- **Synthetic rug-pull benchmark**: mcp-sec-bench class A2 is a rug pull; Cisco mcp-scanner and Ramparts scored 0.00 overall recall — [mcp-sec-bench](https://falc0n007.github.io/mcp-sec-bench/)

### Inferences
- The only documented MCP rug pull in the wild changed code, not tool metadata. Description/schema pinning (TOFU) therefore covers a threat with little real-world evidence so far. Code-level pinning (Docker commits, lockfiles, hash-pinned packages) plus code review covers the observed case. For the study, a "rug pull" fixture should state which layer changes: metadata, code, or remote behavior.
- Pinning only works over time. A one-shot static scan, like zgScanner's single run, cannot detect rug pulls unless it keeps a baseline store. Pinning also cannot see server-side behavior changes behind an unchanged manifest (ACE: 52 of 82 malicious fixtures left `tools/list` unchanged).

### Gaps
- I found no documented in-the-wild case of a tool-**description** rug pull (benign description replaced by a poisoned one after approval). Published examples are demos or synthetic.
- No published false-positive rate for TOFU pinning on legitimate server updates, other than the AppSec Santa "33 mutations, mostly benign" observation.
